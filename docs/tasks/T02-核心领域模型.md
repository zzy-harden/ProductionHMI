# T02：核心领域模型——先把“设备、测点、状态”说清楚

> 这一任务的重点不是学复杂 C++ 语法，而是理解：大型项目为什么要先统一数据模型，再让通信、UI、报警、数据库共同使用。

## 1. 这一任务解决什么问题

如果没有统一模型，很容易出现：

```text
通信层定义一个 Tag
UI 又定义一个 Tag
数据库再定义一个 Tag
```

字段一旦变化，就要到处修改，最后不同模块对“同一个测点”的理解还可能不一致。

所以 T02 先建立：

```text
src/core/domain/
├── DataTypes.h
├── Tag.h
└── Device.h
```

它们只描述业务数据，不做网络、不做界面、不访问数据库。

---

## 2. 必会：什么叫“领域模型”

在本项目里，“领域”就是工业上位机这个业务世界。

我们关心的核心对象有：

```text
设备 Device
测点 Tag
测点实时值 TagValue
设备状态 DeviceState
报警状态 AlarmState
用户角色 UserRole
```

领域模型的作用就是：

> 用 C++ 类型把这些业务概念明确表达出来。

例如“设备是否离线”不应该在不同模块里分别用：

```text
-1
"offline"
false
```

而应该统一为：

```cpp
enum class DeviceState {
    Stopped,
    Ready,
    Running,
    Completed,
    Fault,
    Offline
};
```

---

## 3. 必会：为什么使用 `enum class`

项目里大量使用：

```cpp
enum class Quality { Good, Timeout, Offline, Invalid, Unknown };
```

相较于普通整数，优点是：

- 语义清楚；
- 类型安全；
- 不容易把两个不同枚举混用；
- 调试时更容易理解代码。

例如：

```cpp
Quality quality = Quality::Offline;
```

明显比：

```cpp
int quality = 2;
```

更可靠。

### 面试可答

> 工业软件里状态很多，我倾向用 `enum class` 显式表达有限状态集合，避免魔法数字和隐式整型转换。

## 4. 必会：`TagDefinition` 和 `TagValue` 为什么分开

这是 T02 最重要的设计之一。

### `TagDefinition`：这个测点“是什么”

例如：

```text
名称：主轴转速
地址：100
类型：UInt16
单位：rpm
扫描周期：200ms
报警上限：2500
```

这些是配置，通常不会每 100ms 改一次。

### `TagValue`：这个测点“现在是多少”

例如：

```text
value = 1450
quality = Good
timestamp = 12:30:01.123
```

这是运行时数据，会持续更新。

因此项目把：

```text
定义 Definition
```

和：

```text
实时值 Value
```

分开。

这和很多工业系统里的“点表定义 + 实时点值”思想是一致的。

---

## 5. 必会：为什么实时值必须带 `Quality`

初学者很容易只设计：

```cpp
double value;
```

但工业现场会出现一个关键问题：

> PLC 已经断线了，界面里的 35℃ 到底还是实时温度，还是 10 秒前最后一次读取的旧值？

所以本项目定义：

```cpp
struct TagValue {
    TagId id;
    RawValue value;
    Quality quality;
    timestamp;
};
```

其中质量至少包括：

```text
Good      当前有效
Timeout   本轮请求超时
Offline   设备离线
Invalid   数据无法正确解析
Unknown   还没有拿到首次有效数据
```

### 面试高价值表达

> 上位机不能只展示数值，还要展示数值是否可信。我给实时点值增加时间戳和质量状态，避免通信中断后把旧值继续当作当前有效数据。

这比单纯说“做了断线重连”更有工业软件味道。

## 6. 必会：`std::variant` 是干什么的

项目中的：

```cpp
using RawValue = std::variant<
    int16_t,
    uint16_t,
    int32_t,
    uint32_t,
    float,
    bool>;
```

意思是：

> 一个 `RawValue` 在某一时刻只能保存这些类型中的一种。

为什么不全部存成 `double`？

因为不同测点本身有不同语义：

```text
温度      float
计数器    uint32_t
故障位    bool
有符号值  int16_t
```

`std::variant` 能保留真实类型信息。

初学阶段不用先钻 `std::visit` 的所有写法，只要知道它是 C++17 的“类型安全联合体”。

## 7. 必会：`std::optional` 为什么适合可选配置

`TagDefinition` 里：

```cpp
std::optional<WriteRange> writeRange;
std::optional<AlarmConfig> alarm;
```

不是所有点都有报警，也不是所有点都能写。

相比人为约定：

```cpp
highLimit = -999999; // 表示没配置？
```

`optional` 可以直接表达：

```text
有这个配置
或
没有这个配置
```

使用时可以判断：

```cpp
if (tag.alarm) {
    // 有报警配置
}
```

### 面试可答

> 对业务上天然可缺省的配置使用 `std::optional`，比特殊哨兵值更清晰，也避免把“0”误当成“未配置”。

## 8. `DeviceConfig` 表达了什么

当前设备配置包含：

```cpp
DeviceId id;
std::string name;
std::string ip;
uint16_t port;
uint8_t unitId;
uint32_t timeoutMs;
uint32_t retryCount;
std::vector<TagDefinition> tags;
```

你可以把它理解为：

```text
一台 PLC 的连接参数
+
这台 PLC 下有哪些测点
```

后面的 JSON 配置加载器最终就是为了构造这个对象。

## 9. 为什么 domain 层尽量不依赖 QWidget

当前这些类型使用的是：

- `std::string`；
- `std::vector`；
- `std::variant`；
- `std::optional`；
- `std::chrono`。

而不是把 UI 控件塞进业务模型。

原则是：

```text
领域模型
不应该知道
“界面上有一个表格”
```

以后 UI 只是读取这些数据并展示。

这叫“降低耦合”。
